2. Run 37 — Timbuktu Mode Collapse (86/14)

Run 37 was the direct successor to run 36. The 4-pool buffer was active and the raregoods fraction was set, but the model collapsed heavily toward Timbuktu wins.

MetricValueNotes
Win type split~86% Timbuktu / ~14% Rare goodsSevere mode collapse — Rare goods nearly extinct
Replay buffer — raregoods poolLow fill rateFew natural RG wins meant the pool was starved despite the cross-compensation mechanism

This triggered a new round of interventions. The core insight was that the model needed stronger push toward Rare goods actions during MCTS search itself, not just in the sampling distribution. Three levers were added:

  1. Per-job RG-focused actor selection (rare_goods_actor_fraction) — a fraction of dispatched jobs are tagged as "RG-focused" at dispatch time, using a Bernoulli trial.
  2. Additive heuristic weight for RG jobs (rare_goods_added_heuristic_weight) — RG-focused actors add extra weight on top of the base heuristic, strengthening the RG move bias during MCTS.
  3. Extra tier-1 sims for RG jobs (rare_goods_added_tier1_sims) — RG-focused actors get more MCTS simulations on early-game moves (where collection routing decisions matter).
  4. C++ terminal return bonus for RG wins (rare_goods_bonus) — a terminal return bonus added in C++ so the value head sees a stronger positive signal for Rare goods wins. Requires a C++ rebuild to take effect — see Section 10.

5. New Feature: Per-Job RG-Focused Actor Selection

This is the key anti-collapse mechanism added this session. It operates at job dispatch time in the learner loop.

How it works

  • When a job is dispatched, a Bernoulli trial: random.random() < rare_goods_actor_fraction determines if the job is "RG-focused".
  • RG-focused jobs receive a modified shared_config snapshot with:
    • heuristic_weight = base_weight + rare_goods_added_heuristic_weight (additive override, not replacement)
    • tier1_sims = base_tier1_sims + rare_goods_added_tier1_sims (extra early-game MCTS depth)
  • The actor is unaware of the distinction — it just sees a slightly different config for that game.
  • RG-focused game experiences route to the mcts_raregoods_buffer pool in the replay buffer.

INI parameters (in [MLTraining])

rare_goods_actor_fraction         = 0.30    # 30% of dispatched jobs are RG-focused
rare_goods_added_heuristic_weight = 0.20    # added on top of base heuristic_weight
rare_goods_added_tier1_sims       = 50      # added on top of base tier1 sim count

Tiered MCTS simulation budget (INI-configurable)

The actor's simulation budget is now read from INI rather than hard-coded:

mcts_tier1_sims        = 150    # sims for move_count < tier1_threshold
mcts_tier2_sims        = 300    # sims for tier1_threshold <= move_count < tier2_threshold
mcts_full_sims         = 500    # sims for move_count >= tier2_threshold
mcts_tier1_threshold   = 100    # move count boundary for tier 1
mcts_tier2_threshold   = 300    # move count boundary for tier 2

RG-focused actors add rare_goods_added_tier1_sims only to the tier-1 budget (early-game), since that's where routing decisions are made.

6. New Feature: Job Timeout / Spot VM Resilience

Added to support spot/preemptible VMs on cloud platforms. If an actor VM is killed mid-game, its in-flight job simply disappears — no result is ever returned. Without intervention the learner loop would eventually stall, waiting for jobs that will never arrive.

Mechanism

  • The learner tracks last_result_time, reset each time a game result is received.
  • Periodically (in the Section C idle check), if time.time() - last_result_time > job_timeout_hours * 3600:
    1. Estimate orphaned in-flight jobs: inflight = jobs_dispatched - total_games_processed - job_queue.qsize()
    2. Add inflight to jobs_timed_out (cumulative counter)
    3. Raise the dispatch ceiling: jobs_dispatched < args.num_episodes + jobs_timed_out
    4. Reset last_result_time to avoid immediate re-fire
    5. Log a WARN message with the count

This is intentionally simple: actors are stateless, so preemption just loses the in-progress game. Game checkpointing was considered but rejected — trajectory serialization is complex, the 30-second preemption warning is marginal, and the timeout approach is sufficient for the expected preemption rate.

Configuration

# In mali_ba.ini [MLTraining]:
job_timeout_hours = 3.0    # hours without a result before orphaned jobs are re-queued
python train_mali_ba.py --job_timeout_hours 3.0   # also available as CLI arg
Episode numbering: jobs_timed_out raises the dispatch ceiling but does not affect episode_num or model checkpoint numbering — jobs_dispatched keeps incrementing naturally. The log shows cumulative timed-out count for observability.

8. Replay File Inspection Workflow

Timeout games that reach move 470 with no winner are visually inspectable. The training script can save a full-state replay file for each game it plays.

Enabling replay saving

python train_mali_ba.py --replay_game 1 --replay_dir /path/to/replays/

--replay_game N saves every Nth game (1 = every game). Files are named game_XXXXX.mali_ba_replay and contain the full board state at each move.

Viewing a replay

python main.py --mode gui_replay --replay_file /path/to/game_00001.mali_ba_replay

The GUI replay mode uses SimpleReplayManager (in classes/classes_other.py) which already parses the file format. Navigation: step forward/backward through moves using the GUI controls.

Run 39 purpose: Run 39 was started specifically to collect replay files of timeout games. Visual inspection of what the board looks like at move 470 in a timeout game will help diagnose whether the agents are "almost winning" or completely stuck. The 100% Timbuktu win rate seen so far in run 39 is likely statistical noise (N=20).

9. Multi-Machine Remote Actors — Confirmed Working

The existing queue_server.py / remote_actors.py infrastructure already supports any number of remote machines simultaneously. This was confirmed by reading the source — no changes were needed.

ComponentRoleNotes
queue_server.pyRuns on main/learner machineExposes job queue, result queue, and shared_config over TCP (default port 50000) using multiprocessing.managers
remote_actors.pyRuns on each worker machineTakes --server_host, --server_port, --num_actors, --authkey. Multiple machines can connect to the same server simultaneously.
# On the main/learner machine:
python queue_server.py --host 0.0.0.0 --port 50000 --authkey mysecret

# On each worker machine (can run on multiple machines simultaneously):
python remote_actors.py --server_host <main_ip> --server_port 50000 --num_actors 8 --authkey mysecret

On GCP with all machines in the same VPC, <main_ip> is the internal (10.x.x.x) IP — no firewall rules or NAT required for internal VPC communication.

11. Cloud Training Plan — GCP

Training acceleration via cloud is the immediate next priority. After comparing options (vast.ai vs Google Cloud), the decision was made to try an all-GCP deployment first. If cost is prohibitive, the main machine can fall back to the local desktop with workers on GCP via Tailscale.

Why GCP over vast.ai

vast.aiGoogle Cloud (GCP)
VM preemptionNo preemption mechanism; instances just vanishSpot VMs give 30-second preemption notice; job timeout mechanism handles it
NetworkingPublic internet between machines; need VPN or SSH tunnelsAll-VPC internal networking; machines communicate on 10.x.x.x with no setup
GPU availabilityWide variety; good for short-term rentalMore predictable; reservations available
Setup complexityLower for one-off GPU rentalsHigher initial setup; pays off for sustained multi-machine training
CostOften cheaper for raw GPU-hoursSpot VMs can be competitive; sustained-use discounts help

Planned GCP Architecture

MachineTypeSpot?Role

worker-vm-NCPU instance (e.g., n2-standard-16 or c2-standard-16)Yes (spot)MCTS actors via remote_actors.py. Stateless — preemption loses only the in-progress game.

All machines in the same GCP VPC region. Internal IP communication — no firewall rules needed for port 50000 between VMs in the same VPC.

Installation scripts needed (to be written)

Networking note: queue_server.py must bind to 0.0.0.0 (not 127.0.0.1) for remote workers to connect. The --host 0.0.0.0 flag already exists. Workers use the main VM's internal GCP IP (shown as INTERNAL_IP in gcloud compute instances list).

14. Open Questions / Future Considerations

  • rare_goods_actor_fraction tuning: Current value 0.30 produced 56/44 balance in run 38. If RG wins become plentiful, this can be reduced to 0.15–0.20. If Timbuktu drift resumes, try 0.40.
  • rare_goods_bonus effect: Not yet active (requires C++ rebuild). Expectation is a stronger positive gradient for RG wins in the value head. May amplify the current balance improvement or push further toward RG dominance — watch the split after first run with rebuild.
  • Extended games still not converting: No near-win extended game has ever produced a natural win (last checked at run 38). As the RG value head improves from guaranteed buffer exposure, this should change. If it doesn't change by run 42–43, consider increasing near_win_extension_moves beyond 40.
  • Replay file inspection: Run 39 was collecting replays specifically to inspect timeout games. Look at: how far are pieces from winning at move 470? Are they clustered near a Rare goods win but unable to close? This informs whether the timeout condition itself needs change.
  • Spot VM preemption rate: The job timeout mechanism is conservative (3 hours default). If spot VMs preempt frequently during a training run, the cumulative jobs_timed_out in the log will make this visible. Adjust job_timeout_hours down if preemptions are common and quick.
  • GCP cost monitoring: Set a billing alert before starting the first cloud run. GPU instances are the expensive component — the learner GPU should be on-demand (no preemption), and it's the only one that needs a GPU. Workers are CPU-only.
