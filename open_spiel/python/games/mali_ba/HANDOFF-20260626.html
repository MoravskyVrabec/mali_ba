Root Cause of Run 34 Collapse

The heuristic guidance (which favours rare-goods-directed moves) was decaying too quickly (decay_end=500). Once it dropped below 0.14, the early self-play games stopped finding Rare goods wins, and the buffer filled with Timbuktu experiences. The model had no signal to push it back toward Rare goods.

Remediation applied before run 35:

  • heuristic_guidance_decay_end extended from 500 to 2000
  • Extension threshold raised from 0.20 to 0.30 (avoid extending low-confidence games)
  • Buffer manually resized to 50,000
  • new_rare_region_reward = 0.30 (already in place for prior runs)

4. Timbuktu Mode Collapse — Diagnosis

A self-reinforcing feedback loop is preventing the model from improving at Rare goods wins:

  1. Rare goods wins require broader board strategy and take more moves to achieve than Timbuktu wins.
  2. MCTS finds Timbuktu wins more easily → buffer accumulates proportionally more Timbuktu experience.
  3. Model trains more on Timbuktu → value head and policy both optimise for Timbuktu.
  4. Self-play produces even more Timbuktu wins → buffer skews further.
  5. Rare goods value head stays negative → MCTS cannot be guided toward Rare goods → loop repeats.

The bootstrap buffer (95.5% Rare goods) was designed to break this loop, but at 11% of total training data it is no longer dominant enough to counterbalance 74% Timbuktu in self-play. Extending heuristic_guidance_decay_end to 2000 helped but did not fully prevent the drift seen in run 35's final windows.

5. Fix — Dedicated Rare Goods Buffer Pool

The structural fix is a guaranteed per-batch sampling fraction for Rare goods wins, achieved by adding a fourth replay buffer pool: mcts_raregoods_buffer.

5a. Routing Logic

In train_mali_ba.py's learner loop, is_rare_goods_game is detected as:

is_rare_goods_game = (any(r >= 1.0 for r in returns)
                      and not is_bootstrap_game
                      and 'Timbuktu' not in finished_msg)

Experience tuples now carry a 6th element: (obs, policy, value, is_bootstrap, is_near_win, is_rare_goods). The trainer routes on priority: bootstrap → nearwin (timeout only) → raregoods → natural.

5b. Sampling Guarantee

In ReplayBuffer.sample(), raregoods_pool_fraction of the MCTS batch target is drawn from mcts_raregoods_buffer before the natural pool fills the remainder. When the raregoods pool is short (early in a run), cross-compensation draws from the natural pool instead — the batch size is always met.

5c. Buffer Migration

Old saved buffers (from runs ≤ 35) do not have a mcts_raregoods_buffer key. On first load after the upgrade, the trainer automatically splits the existing mcts_natural_buffer 50/50 to seed both pools. The pools then self-correct over time via normal FIFO eviction: new Timbuktu wins fill mcts_natural_buffer and new Rare goods wins fill mcts_raregoods_buffer.

Trainer: Migrating old buffer — split 30480 natural entries 50/50 into natural (15240) and raregoods (15240) pools.

7. Extension Threshold — Run 36 Plan

No extended game has ever produced a natural win across all runs to date. Timeout games extending from 430 → 470 moves are generating near-win training data, but none have converted to an actual win condition. Possible explanations:

  • 430-move games are genuinely not close enough — the near-win flag fires on structural proximity (≥4 rare good regions) but the final trigger requires additional moves that fall outside the extension window.
  • The value threshold (0.30) correctly identifies interesting games, but 40 extra moves is still insufficient for this position class.

Run 36 plan: Raise near_win_extension_value_thresh to 0.40. This further restricts extension to games where the value head is highly confident, filtering out marginal extensions that are unlikely to convert. If extended games start producing natural wins (as the Rare goods value head improves), the threshold can be lowered again.

8. Near-Win Extension — Reference

Logic unchanged since the 2026-06-24 handoff. The check runs at exactly move_count == base_max_play_moves (430):

  1. Evaluate is_near_win(near_win_rare_regions) and value head.
  2. If (near_win OR clear_winner) AND max_val > near_win_extension_value_thresh: log extension message, loop continues.
  3. Otherwise: early_terminated = True; break — game discarded.

C++ IsTerminal() and the win-condition evaluator both use GetMaxPlayMoves() + GetNearWinExtensionMoves() (= 430 + 40 = 470) — this is the fix from the 06/24 session and is now compiled and confirmed working.

10. Actor Loop — Tiered MCTS Simulation Budget

Each actor dynamically adjusts bot.max_simulations based on move_count within the play phase. The intent is to reduce compute on early moves (where the game tree is wide but positions are less critical) and concentrate deeper search on mid-to-late game positions where the value head starts to discriminate.

if move_count < 100:
    bot.max_simulations = 150
elif move_count < 300:
    bot.max_simulations = 300
else:
    bot.max_simulations = getattr(args, 'max_simulations', 500)   # full budget

The --max_simulations CLI argument (default 500) is only the ceiling, applied from move 300 onward. Early moves run at 150 sims and mid-game at 300 sims. This is hard-coded in train_mali_ba.py rather than exposed in the INI.

13. Open Questions / Future Considerations

  • Local vs remote actor win rate gap (69.2% vs 27.8% in run 35): not yet investigated. Possibly weight update lag on remote actors, or different compute budget affecting MCTS quality. Worth correlating actor ID with win rate across more runs.
  • Trigger ≠ Winner for Rare goods (33.3% of Rare goods wins): one player triggers the Rare goods end condition but a different player wins on overall score. This is expected by game rules (trigger ends the game; winner is determined by score). It is not a bug, but worth confirming the game is correctly recording who holds the most rare goods at game end.
  • Extended game natural wins: the extension has never produced a natural win. Once the Rare goods value head improves (expected from run 36's guaranteed exposure), near-win extended games should start converting. If they still don't, consider increasing near_win_extension_moves beyond 40.
  • raregoods_pool_fraction = 0.40 is aggressive (equal weight to Timbuktu in MCTS). If Rare goods wins become plentiful and the mode collapse resolves, this can be reduced to 0.20–0.25 to allow the natural distribution to re-emerge.
