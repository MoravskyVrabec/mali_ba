1. The short version

  1. For months the network learned nothing measurable. Checkpoints from July to late September were no better than v101, both in the policy probe and head to head.
  2. We found and fixed a series of real bugs along the way. The value target was unlearnable (gamma 0.997 with no progress plane). The convolution axes were transposed. Every actor replayed the same meeple layout. The analysis tool mismatched games and results. Self-play was 7× slower than it needed to be.
  3. The underlying problem was memorization. The 100k-position buffer held only about 240 games, and the value head learned to recognise which game a position came from: 100% on games it trained on, about 50% (a coin flip) on new games.
  4. More games fixed it, not a different architecture. Pretraining on about 9,000 heuristic games, and keeping only 1 position in 16 per game in the buffer, took the value head to about 70–76% on MCTS games it had never seen.
  5. Holding heuristic guidance at 0.30 stopped the win rate collapsing. D005 is the first run in which the agent measurably improves during training: more wins, and earlier recognition of them.
  6. Next: make the search decisive enough for the policy to learn. The first step is a head-to-head test of a lower uct_c.

2. Timeline: run 113 → A → B → C → D

  1. to 25 Sep

    Run 113 and earlier no measurable learning

    The value target used gamma = 0.997 over games of about 420 moves, and the observation had no move-count plane. So a certain win's target ranged from +0.22 to +1.12 depending on how far away the end was, which the network couldn't see. Twenty moves from the end it rated soon-to-be Timbuktu winners (+0.26) below timeout leaders (+0.43). Self-play cost about 37 ms per network call, because actors run TensorFlow single-threaded on the CPU.

  2. 25–27 Sep

    Infrastructure, then the A series (A001–A005)

    • gamma became configurable and was set to 1.0, with rewards rescaled to fit the value head's range. The timeout leader's reward became configurable too.
    • Self-play got 7× faster with a batched GPU inference server (inference_server.py), on top of a 4.2× gain from caching and compiling MCTS inference. Remote workers were added.
    • The first policy probe (8 checkpoints, July to September) found none better than v101. Head to head, vA004 against v113 scored 0.336 against a null of 0.333.
    • Lesson: a rising loss curve means the buffer is filling, and a flat loss can't show strength in either direction.
  3. 27–30 Sep

    The B series (B001–B008) axis fix

    • Conv axis order fixed. Keras read the board width as the channel axis. A Permute now feeds (height, width, planes). All weights were invalidated; buffers weren't.
    • Move-count plane added (96 planes), so the network can see how far the game has gone.
    • analyze_log join bug fixed: 26% of games had been paired with another game's result, so earlier value plots were wrong.
    • B008 rebalanced the buffer pools. skip_timeout_games had made training batches 88% wins while real games were 88% timeouts.
  4. 30 Sep

    Reproducibility fixes

    • Every game from one game object used the same meeple layout, so a run had only about 100 distinct boards. The layout is now a recorded chance outcome with 65,536 possibilities.
    • Probe v2: a frozen set of 600 positions scored against a search with no network in it, exactly repeatable. Untrained 192-plane floor: 24.8% ± 7.8 top-1, best untrained init 32.2%.
  5. 30 Sep – 1 Oct

    The C series (C001–C004)

    • 192-plane observations: each seat's score, the seat to move, and every seat's common and rare goods.
    • Buffer work: pool shares scale with how full each pool is; a separate Timbuktu-win pool (10%); "natural" renamed to "timeout"; resize_buffer.py and strip_bootstrap.py updated.
    • Culling recalibrated. C003 had thrown away 91% of its games using thresholds set for an older value head.
    • Inference server: XLA plus semaphore wake-ups cut the laptop's per-simulation time from 6–9 ms to 3.7 ms.
    • Results: probe 33–34% (not significant); value head picked the winner 52–53% of the time in-game. Then the diagnosis below.
  6. 1–2 Oct

    The D series first measurable learning

    Heuristic pretraining, a thinned buffer (1 position in 16 per game), a slower training rate, and guidance held at 0.30. D003 and D005 are runs; vD001, vD002 and vD004 are pretraining checkpoints. Details in section 4.

3. The key discovery: memorization

On C004 we tested the value head on fresh games it had never seen. The result was clear-cut:

Who is picked as the eventual winner (last 20 moves)games it trained onheld-out gamesfresh games
C004 value head~100%~66–71%48–55%
Simply reading the score planes (no network)89%88%90%

Why: the buffer kept every move of every game, so 100k positions covered only 240 games. All of a game's roughly 400 positions look alike and share one outcome. Recognising "this is game #57, seat 2 wins" is easier than learning "whoever leads on points usually wins". Every value network we tried did the same thing: the old architecture, a direct path for global features, and L2 weight decay.

What fixed it was data volume. Trained on about 9,200 heuristic games, the same networks picked the winner of the 240 MCTS games they'd never seen 71–78% of the time. Architecture made little difference there. Even 9,200 games get memorized after enough passes, so pretraining keeps the best held-out step instead of the last.

4. The D series in detail

What was built (all committed)

  • pretrain_heuristic.py: generates heuristic games in parallel (15% random moves, 1 position in 16 kept), trains policy and/or value with whole games held out, keeps each head's best step, and writes a normal checkpoint.
    • --eval_buffer scores each step on a saved MCTS buffer, and by default the value head is chosen by its error there.
    • --heads value --init_from … --fresh_value retrains only the value head.
    • --min_wins / --win_keep_every enrich the data with wins, weighted back to their natural rate.
  • buffer_keep_every (trainer, ini): keeps 1 position in N from each game. Saved buffers record N; a buffer saved with less thinning is thinned to match on load, and never thinned twice.
  • load_model treats a weights file that doesn't fit the network like a missing one, instead of half-loading it.
  • analyze_log calibration compares predictions with training targets; its "experiences added" count accounts for thinning.

5. Why the policy isn't learning

Probe v2 on 590 positions: every checkpoint scores 32–36% top-1, and none differ significantly (McNemar p 0.08–1.0). That's still inside the untrained range. Every policy also sits at about 92% of uniform entropy: it barely prefers one move over another.

Checkpointtop-1entropy (share of uniform)
vC00435.9%91%
vD004 (D005's start)31.9%92%
D005 checkpoints, 12:56 to latest33.1–35.9%92%

The network is faithfully learning flat targets. The heuristic's move weights (the pretraining target) are 91% of uniform (98% median). MCTS visit targets in D005's buffer are 90–91% (96% median), with only about 7 legal moves per position.

Why the search is flat. At each position, the children's Q values typically differ by about 0.04; the value head's predictions are compressed. With uct_c = 2.0 the exploration term is far larger than that, so visits follow the prior, which is itself flat. Measured with search_sharpness.py (D005 18:56 checkpoint, 120 positions, 300 sims):

Sharper isn't automatically better. A lower uct_c makes the search trust a value head that is about 70% accurate. Whether the moves it then chooses are stronger has to be settled by head-to-head play before it goes into a run.

6. The plan

  1. On return: read D005

    Run analyze_log.py train_runD005.log and look at:

    • the win rate trend: still 17–21%, or rising again?
    • the leader's predicted value in Timbuktu and rare-goods wins: still climbing from about −0.07?
    • top-pick: around 69%?

    Probe the newest checkpoints against vD004 for completeness. If it's plateaued, stop D005 when convenient; its latest checkpoint is the starting point for what follows.

  2. Head-to-head test of uct_c

    • Small change first: ab_eval.py currently uses one uct_c for both sides; add --uct_c_a / --uct_c_b.
    • The test: play the same D005 checkpoint at 2.0 against 0.5, and possibly 2.0 against 1.0, with the run's simulation counts and guidance 0.30.
    • Cost: about 300–700 games to show a moderate difference. Run it with D005 stopped, so it has the machine.

  3. If the lower uct_c wins: run D006 with it

    • Add uct_c to the ini. It's command-line only today (--uct_c, default 2.0, passed on to remote actors).
    • Start from D005's latest checkpoint.
    • What success looks like: the policy's entropy in the probe falling below 92%, top-1 rising past the untrained range (above about 36%), and the win rate holding or rising.

  4. If lowering uct_c doesn't help, or makes play worse: normalize Q per node

    The MuZero approach: rescale the children's Q values to 0–1 within each node before applying the exploration term. Small value differences then count however compressed the value head is. It needs a custom child-selection function for OpenSpiel's MCTS. Sharpening the policy targets (visits raised to a power) is a cheaper fallback, but it only makes flat preferences look confident.

  5. Later: train harder

    train_interval_seconds = 8 was chosen to stop the network memorizing a 240-game buffer. The thinned buffer now spans about 3,900 games, so once the policy has a real signal, try 4 seconds and watch in-game top-pick for any drop.

  6. Housekeeping

    • Commit mali_ba.ini once you're happy with the D-series settings (they're uncommitted; see below).
    • Rsync Python changes to the laptop before each run, and rebuild there after any C++ change.
    • pretrain_data/ holds 56 GB of generated games (22 GB for the first 10k-game set, 34 GB for the win-enriched set) and is gitignored. Delete the folders you no longer need.

9. Things that misled us (don't repeat)

  • Loss curves and self-play win rate don't measure strength. Use the probe or head-to-head play.
  • A value head can look excellent on its own buffer and be useless on new games. Always test on held-out or fresh games.
  • Benchmarks without the actors' single-thread settings (OMP_NUM_THREADS=1) read about 20× too fast.
  • Old probe sets and old value-check CSVs are unreliable: different boards per process, and games joined to the wrong results.
  • Never take legal_actions()[0] at the opening chance node; sample the layout.
  • Python's configparser crashes on inline ini comments (key = value # note). Comments go on their own line.
  • "Mean |err|" rising across thirds can be a change in the win/timeout mix, not a decline. Split by outcome type before concluding anything.
