Mali-Ba Training Handoff — 2026-07-25

This document updates HANDOFF-20260630.html. It covers everything worked on since then except VM/cloud-provisioning mechanics, which now live in HANDOFF-VM-SETUP.MD (formerly HANDOFF-GCP-SETUP.md, now covering both GCP and Hetzner). This document is entirely about the training/model side: reward structure, a real replay-file bug, buffer dynamics, a CPU throughput fix with a measured ~25-29% effect, MCTS search-budget diagnostics grounded in real buffer data, and value-head/policy analysis.

Where things stand: the core open question from 06-30 — extended near-win games essentially never converting to actual wins — got a real diagnosis this session: a reward-structure mis-specification (approaching a win paid almost as much as winning) plus a genuine MCTS search-budget shortfall at the specific decision that closes out a win (trade-route declaration, up to 300 legal candidates — more branching than any other decision in the game). Both have been addressed in code/config. Current win rate sits around 20-30% and is still noisy run to run; several confounded rounds of tuning (buffer size, heuristic guidance, sim budget) make attribution hard, which is itself a lesson documented below.

1. Reward Structure Overhaul

Read straight from the actual Returns()/Rewards() implementation (mali_ba_state_core.cc), not assumption. Two structural problems were found:

SignalOld valueNew valueWhen
Win (highest score)+1.0+1.0 (unchanged)terminal
Loss−0.1−0.1 (unchanged)terminal
Timeout penalty (all players)−0.7−1.2terminal, on top of the above
Rare good from new region+0.30 each+0.05 eachduring play
Rare-goods win bonus0.0 (disabled)+0.2terminal, only on rare-goods win

Problem 1 — approaching the win paid almost as much as winning. new_rare_region_reward = 0.30 could pay out up to 6 times — a player farming rare goods from 5-6 regions banked +1.5 to +1.8 in cumulative shaping without ever ending the game, more than the +1.0 win itself. The value head was learning "trajectories that approach the win are high-value," which is exactly what the data showed: high value estimates near the move cap, 0% conversion to an actual win.

Problem 2 — being ahead at timeout was still profitable. At timeout the leader still got scored normally (+1.0), then −0.7 applied to everyone — netting +0.3 for stalling instead of closing. The model was never taught "a win you don't close isn't a win." This also connects to a real finding from manual replay review (game 125): two different players had independently built geographically-obvious paths to the same win condition, and neither converged — stalling was a rational equilibrium of the reward structure at the time, not necessarily a search failure on its own.

Buffer-composition detour that shaped this diagnosis: an earlier hypothesis ("rare completions are just scarce in the buffer") was directly falsified by checking actual buffer composition — the two win-condition pools held 28,800 of 40,000 experiences (72%) at the time, not a scarce trickle. The real story was data-quality (what those experiences reward), not data quantity.

Changes made, and why in this order

  1. max_moves_penalty: −0.7 → −1.2. Makes timeout strictly unprofitable even for the leader (nets 0.0 to −0.2 instead of +0.3), while losing-by-closing (−0.1) still beats losing-at-timeout (≈−1.1), so trailing players still prefer to close rather than stall.
  2. new_rare_region_reward: 0.30 → 0.05, plus rare_goods_bonus: 0.0 → 0.2 (already implemented in C++ from the prior session, just never turned on). Moves the incentive from "approaching" to "actually winning by rare goods."

Two further recommendations from the original analysis were not implemented this session — logged here for later:

  • Reward the closer, conditional on winning — a small terminal bonus to whoever triggered game end, only if they also won (GetGameEndTriggeringPlayer() already exists in C++). Not done; see §8 for why the trigger-vs-winner data suggests this may be less necessary than first thought.
  • Widen the loss differential / margin-aware returns — −0.1 for losing barely distinguishes 2nd from 3rd place. Considered valuable but not attempted; would require re-tuning every threshold in the pipeline that's denominated in return units (clear_winner_thresh, the hopeless-check thresholds, near_win_extension_value_thresh).
Buffer resize interaction: the replay buffer was deliberately shrunk (40,000 → 20,000, briefly → 10,000) at the same time as the reward change, specifically to flush old-reward-structure experiences out of the FIFO pools faster. The math actually works out cleanly: once cumulative new insertions into a pool exceed its capacity, every resident experience postdates the change — it's a hard cutoff, not a gradual dilution. See §3 for the full buffer discussion.

2. Replay File Format Bug — Fixed (C++ + Python)

The GUI replay loader crashed with RuntimeError: Failed to obtain valid_hexes on a run started with --replay_game enabled. Root cause: the Python writer's [setup]-section call used .serialize() (a generic per-move serializer) instead of the purpose-built CreateSetupJson(), which was the only place that actually wrote valid_hexes/cities/grid_radius/num_players into the setup block. The call site using the correct method appears to have been dead code, never actually reached by the real writer.

Fix (permanent, C++ + pybind11 + Python)

  • mali_ba_state_moves.cc — CreateSetupJson() rewritten to build on top of json::parse(Serialize()) rather than a fresh empty object, then layer the static board-config fields on top. Combines both code paths instead of leaving one dead.
  • games_mali_ba.cc (pybind11) — exposed the method: .def("create_setup_json", &mali_ba::Mali_BaState::CreateSetupJson).
  • train_mali_ba.py — the [setup]-section writer switched from .serialize() to .create_setup_json().

Temporary fallback (still present, safe to remove once confirmed unnecessary)

main.py's MODE_GUI_REPLAY branch: if a loaded replay's setup data is still missing the required keys (i.e. an old replay file written before the fix), it falls back to constructing a live GameInterface from the ini and backfilling the missing keys via setdefault(). Only matters for replay files generated before this fix landed.

Rebuild-propagation landmine hit during this fix: after editing games_mali_ba.cc, rebuilds kept silently failing to pick up the new binding. Root cause: open_spiel/python/pybind11/games_mali_ba.cc in the actual build tree was a plain copied file, not a symlink — unlike open_spiel/games/mali_ba/ and open_spiel/python/games/mali_ba/, which are symlinked back to the dev tree and update automatically. Fixed by re-copying the current dev-tree file over the stale build-tree one. If pybind11-layer C++ changes ever seem to "not take" after a real rebuild, check this first — it's a structural gap in the symlink scheme (see apply_open_spiel_edits.sh, which only handles CMakeLists.txt/pyspiel.cc wiring, not this file's placement).

3. Replay Buffer — Sizing and FIFO Turnover Dynamics

Date/contextreplay_buffer_sizeWhy
Pre-session baseline40,000—
After reward-structure change20,000Halve every pool's size to flush old-reward-structure experiences roughly 2x faster
Briefly10,000Even faster flush, tested transiently
Current24,000Expanded back up modestly once the reward-structure transition was judged complete, trading flush-speed for more sample diversity

Pool sizes are fractions of the total (mcts_buffer_fraction, near_win_pool_fraction, raregoods_pool_fraction — see ini [MLTraining]). At the 20,000 setting: natural (Timbuktu) and raregoods pools were 8,000 each, near-win 4,000. mcts_buffer_fraction is now 1.00 (bootstrap pool effectively disabled — bootstrap_episodes=0 in current run commands).

Key mechanic: only wins and near-win timeouts feed the buffer

With --skip_timeout_games set (used in every run command this session), a plain (non-near-win) timeout contributes zero experiences to any pool — its trajectory is discarded entirely (continue, never queued). Only near-win timeouts (flagged via is_near_win(), checking rare-goods region count at the terminal state) survive, and they go into the separate near-win pool, not natural/raregoods. This matters a lot for reasoning about buffer turnover: win-pool refresh rate is bounded by actual win rate, not overall game-completion rate.

FIFO turnover is a hard cutoff, not gradual dilution

Once cumulative new insertions into a pool exceed its capacity, the entire resident pool postdates whatever changed. This was used directly to settle a debate about whether stale reward-structure data was still contaminating training: with the buffer at 20,000 (natural/raregoods caps of 8,000 each), insertion counts of ~14,500 (Timbuktu) and ~13,700 (rare goods) over the relevant window both exceeded their pool's capacity — meaning the buffer was fully turned over, not partially. This resolved what looked like conflicting theories about a training plateau (see §8) with hard arithmetic instead of guessing.

4. CPU Thread Oversubscription Fix — Measured ~25-29% Throughput Gain

Discovered by chance while investigating laptop overheating during a threading-conscious actor-count discussion. Neither remote_actors.py nor train_mali_ba.py's actor path set any thread-count environment variables, so each actor process's own TensorFlow/BLAS stack spawned its own internal thread pool independently.

Measured severity

Sample actor subprocess thread count: 50
Total actor subprocesses on a 16-core box: 16
Total OS threads across all actors: 752   (47:1 oversubscription vs. 16 physical cores)

The fix

export OMP_NUM_THREADS=1
export TF_NUM_INTRAOP_THREADS=1
export TF_NUM_INTEROP_THREADS=1

Applied first as a manual env-var wrapper on one Hetzner worker (hetzner-2) as a controlled A/B against an identical unfixed worker (hetzner-1), same hardware, same code, started minutes apart:

MachineAvg time to move 230
Hetzner-1 (unfixed baseline)66.7 min
Hetzner-2 (thread-limited)47.6 min — 28.6% faster

Corroborated independently on the desktop's local actors, comparing run105 (unfixed) vs. run106 (thread-limited, applied as a blanket shell-level env var covering both actors and the trainer's own process at the time): 23.3% faster — close enough to the Hetzner number to trust the effect is real, not one machine's fluke.

Side effect caught and separately fixed: applying the env vars as a blanket shell-level wrapper (covering the whole process tree) also throttled the trainer's own gradient-step computation, since it's launched from the same command — training-cycle cadence measurably slowed (~30s → ~40s). The trainer's batched gradient step is a different workload than actor inference (one large computation vs. many small independent ones) and plausibly benefits from multi-threading rather than being forced to one thread.

Permanent fix — code-level, not env-var

train_mali_ba.py's actor_process() now sets the three env vars via os.environ.setdefault(...) immediately before its own (function-local) import tensorflow, i.e. before TF's thread pools initialize. Because actors are spawned via mp.set_start_method('spawn') (fresh interpreter per process) and remote_actors.py imports and reuses this exact function, every actor — local, laptop, GCP, or Hetzner — picks this up automatically, with zero manual env-var setup needed going forward. The trainer process is a separate mp.Process with its own later TF import, so it's unaffected and keeps full multi-threading — after this fix landed, the desktop's own training-cycle cadence actually became faster than its original pre-fix baseline (~14s vs. the original ~30s), likely because actors no longer contend with the trainer's threads for the same cores.

5. MCTS Simulation Budget — Diagnosed From Real Buffer Data, Not Guesswork

The question: is the tiered sim budget actually well-targeted?

Existing tiers ([MLTraining]): sim_tier1_sims (moves 0 to sim_tier2_start), sim_tier2_sims (to sim_tier3_start), sim_tier3_sims (beyond). All keyed on move number.

Measured: MCTS isn't converging well at the highest-branching decision

Declaring a trade route (OPTIONAL_ROUTE phase) can have up to 300 legal candidates — by far the largest branching factor of any decision in the game (mancala steps: ≤6; play-phase choices: <20). Pulled 1,241 real route-declaration decisions directly from the replay buffer and measured MCTS visit-count concentration (the policy training target itself):

MetricMeanMedian
Candidates with any visits (of up to 300 legal)26.69
Top-1 candidate's share of total visits0.3150.211
Normalized entropy of the distribution (1.0 = uniform/undecided)0.7620.932

A median top choice capturing only ~21% of visits, with entropy near-maximal, means the search is typically still splitting attention across several candidates rather than converging — even at what was, at the time of measurement, a fairly generous simulation budget. For reference, AlphaZero's original Go implementation used 800 sims/move for a comparably-sized branching factor (~250-300), but with a far more mature, extensively-trained network — a noisier/less-trained prior generally needs more search to compensate, not the same amount.

A real bug found by a sharp follow-up question, and fixed

An earlier version of this analysis claimed "50% of route declarations happen before move 100." This was wrong — a real extraction bug (a two-stage grep accidentally extracted player IDs 0/1/2 alongside move numbers, flooding the dataset with spurious tiny "move numbers"). Corrected extraction: route declarations essentially never happen before move ~99 (structurally sound — declaring a route needs 3+ connected trading centers, which takes many turns to build). The real distribution: median move 281, 59.2% happen before move 300 (i.e. in tier2, not getting the larger tier3 budget) — a smaller, differently-shaped problem than first reported, but still a real one.

Fix: phase-keyed sim floor (not move-tier-based)

Since route-declaration branching doesn't track move number the way other decisions roughly do, a move-tier boundary can't target it well no matter where the boundary sits. Added a phase check in train_mali_ba.py's actor loop, applied after the existing move-tier logic computes its value:

# Route-decision floor: OPTIONAL_ROUTE decisions with enough candidates
# get AT LEAST sim_route_decision_sims, but never less than whatever
# the move-tier above already provides (e.g. tier3's late-game budget).
if pyspiel.mali_ba.downcast_state(state).current_phase() == pyspiel.mali_ba.Phase.OPTIONAL_ROUTE:
    n_route_candidates = len(state.legal_actions())
    if n_route_candidates >= getattr(args, 'sim_route_decision_min_candidates', 20):
        bot.max_simulations = max(bot.max_simulations,
                                   getattr(args, 'sim_route_decision_sims', 500))
Bug caught mid-implementation, before it shipped: the first version of this fix unconditionally overrode to sim_route_decision_sims rather than taking the max — which would have reduced the budget for late-game route decisions below whatever tier3 already provided (tier3 is now 1100; the floor is 600). Caught by a direct question ("does the higher end-game number override this?") before the run using it was even started. Worth remembering as a pattern: this kind of "new override silently undercuts an existing higher value" bug is easy to introduce and easy to miss without re-reading the actual logic.

New ini keys ([MLTraining]):

sim_route_decision_sims = 600               # floor for qualifying route decisions
sim_route_decision_min_candidates = 20      # only decisions with this many+ legal actions qualify

Only applies when candidate count is large enough to justify the cost — cheap/easy route decisions (few candidates) fall through to the normal move-tier budget, so the fix targets its cost at the genuinely hard decisions rather than uniformly taxing all ~14,000+ route declarations seen in a typical run.

6. Heuristic Guidance Weight — Counterintuitive Findings

heuristic_guidance_weight blends heuristic move-scoring into the MCTS prior (0 = pure network, 1 = pure heuristic), originally on a decay schedule (0.15 → 0.10 over MCTS games 100-2000).

Finding 1: the decay wasn't hurting performance — evidence pointed the opposite way

Directly aligned win-rate-by-quintile against the actual observed heuristic weight at that point in time (not the nominal schedule):

QuintileHeuristic weightWin%
Q10.14714.1%
Q20.14516.1%
Q30.13620.3%
Q40.12722.4%
Q50.11719.8% (small dip, single data point)

For 4 of 5 quintiles, win rate rose as heuristic weight fell — the opposite of what "declining guidance hurts performance" would predict.

Finding 2: heavier heuristic weight still helps right now, just not narrowly

A different comparison — rare-goods-focused games (elevated heuristic weight, currently base 0.13 + up to 0.05 added) vs. normal games, same time window, across two full runs:

RunGroupnWin%Rare winsTimbuktu wins
108RARE-GOODS-FOCUSED41124.6%10.2%14.4%
108Normal84516.0%6.0%9.9%
109RARE-GOODS-FOCUSED4731.9%10.6%21.3%
109Normal8724.1%4.6%19.5%

Focused games won more overall in both runs — not just more rare-goods wins, but more Timbuktu wins too. This is evidence against a "sims fighting the heuristic" hypothesis (which predicted focused games doing worse under a heavier search budget) and instead suggests heavier heuristic weight currently just makes play more decisive/purposeful across the board, consistent with the network still being early in its own development.

Current settings and the reasoning behind them

heuristic_guidance_weight       = 0.13   # was decaying 0.15 -> 0.10
heuristic_guidance_weight_final = 0.13   # now held flat -- decay disabled
rare_goods_added_heuristic_weight = 0.050   # was 0.20-0.30 earlier in the session

Given both findings above, the working plan discussed (not yet implemented) is: don't just hold guidance at a fixed level indefinitely and wait passively for "signs of readiness" — periodically test a small held-out low-guidance batch against the main heavily-guided fleet. If the low-guidance batch's win rate holds up, that's real evidence of independent network skill and guidance can be safely reduced; if it collapses, heavier guidance is still buying something genuine. Not yet built.

8. Value Head / Policy Diagnostics

Trigger player vs. actual winner

Confirmed empirically (matching win-condition games to their log FINISHED lines via a game-length/winner/win-type composite key): the player who triggers game end is the actual winner 75.6% of the time (59/78 matched games) — meaning 24.4% of wins are triggered by someone other than the eventual winner. In those 19 mismatch games, the value head's average prediction consistently favored the actual winner over the triggerer at every checkpoint measured (e.g. at move 380: 0.130 for the winner vs. −0.242 for the triggerer) — a genuinely positive sign that the value head tracks real point-standing rather than just reacting to whoever ends the game.

Value-head trend across a run: no clean monotonic improvement

Repeated quartile/quintile breakdowns of predicted winner-value at fixed move checkpoints (200/260/320/380), split by win type, across several runs. Consistent pattern: not a monotonic trend in either direction — a rise-then-crash-then-partial-recovery shape, most pronounced for Rare Goods wins. A two-bin (early-half/late-half) comparison can mask this entirely by averaging a peak and a trough together; the finer-grained multi-quantile breakdown was necessary to see the real shape.

Policy vs. value asymmetry: Timbuktu vs. Rare Goods

An observation from manual review, then substantiated with data: without the rare-goods heuristic bias, the policy drifts toward Timbuktu wins — but the value head has an easier time recognizing an approaching Rare Goods win than a Timbuktu one. Checked directly: of 14 long (>380-move) Timbuktu wins, 13 were also flagged near_win (the rare-goods-region condition) at move 380, even though they ultimately won via the Timbuktu route. Average predicted value at move 380: Timbuktu wins ≈0.18, Rare Goods wins ≈0.30 — same order of magnitude, not two sharply distinct signatures.

Working explanation, not fully proven: key_location_post_reward gives the policy a dense, geographically-targeted training signal specifically toward the Timbuktu-route waypoints (Timbuktu, Agadez, Oudane, coast), while rare-goods progress ("how many distinct good types held") is an easier static recognition target for the value head than route-connectivity (a spatial/graph reasoning problem). The two heads may simply have specialized differently based on which signal was easiest to learn from, not because either is "confused."

9. Open Questions / Next Steps

  • Route-decision sim floor (600) not yet validated — rerun the buffer visit-concentration measurement (§5) after enough games have accumulated under the new floor, to see whether top-1 visit share / entropy actually improved. Same methodology, clean before/after comparison possible.
  • Held-out low-guidance test batch (§6) — proposed but not built. Would give a principled, evidence-based signal for when to reduce heuristic guidance further, rather than the ad-hoc decay schedule or an indefinite flat hold.
  • Near-win → actual-win conversion rate tracking — still not built into analyze_log.py as a standing report (confirmed absent this session); would directly measure whether the reward-structure fix moved the needle on the original 0%-conversion finding from before this session.
  • Multiple confounded changes stacked together — buffer size, heuristic weight, and sim budget were all changed together at least once this session (acknowledged explicitly at the time), meaning credit/blame for the resulting win-rate movement can't be cleanly attributed to any one of them. Current combined config is the new baseline to hold steady against, per the pattern established earlier in the session (protect a clean read once one exists, rather than continuously stacking new changes on top).
  • Checkpoint-vs-checkpoint head-to-head evaluation — proposed as the most rigorous way to verify actual model improvement (load two saved weight files, play them against each other, track win rate) — the only analysis that doesn't rely on the model grading its own self-generated data. Not built; flagged as valuable but currently deprioritized given compute constraints.
  • Hetzner capacity exhaustion — unresolved as of this writing; see HANDOFF-VM-SETUP.MD §9 for full detail and current status.
