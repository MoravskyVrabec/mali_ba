## Project Overview

Mali-Ba is a 3-player board game implemented inside OpenSpiel. An AlphaZero-style training
pipeline (`train_mali_ba.py`) trains a neural network to play it using MCTS self-play.
Training runs on a desktop machine (192.168.0.102) with optional remote actors on a
laptop (192.168.0.241).

## Income Farming Problem & The No-Consecutive-Income Rule

### The problem
When `heuristic_guidance_weight` drops below ~0.05, the NN defaults to spamming
TakeIncome on every turn. TakeIncome yields reliable intermediate rewards (common goods)
but none of the players advance toward the end-game win triggers. Win rate collapses to 0%.

### Training heuristic just added (requires rebuild)
A rule was added to `mali_ba_state_core.cc` and `mali_ba_state.h` that **blocks a player
from taking income twice in a row on their own turns**.

**This is NOT a real game rule — it is a temporary training heuristic only.**
It is clearly commented as such in the code. Remove it once the NN has learned to pursue
win conditions without it.

**Files changed:**
- `open_spiel/games/mali_ba/mali_ba_state.h` — added `std::array<bool, 3> last_was_income_`
  to `StateSnapshot` struct and to the state class (initialized `{false, false, false}`)
- `open_spiel/games/mali_ba/mali_ba_state_core.cc`:
  - `PushStateToUndoStack` — saves `last_was_income_` in snapshot
  - `UndoAction` — restores it from snapshot
  - `DoApplyAction` (kPlay) — sets `last_was_income_[current_player_id_]` true/false
  - `GetLegalActionsAndCounts` — blocks income if `last_was_income_[current_player_id_]`

**Edge case:** if a player has no legal moves except TakeIncome on two consecutive turns,
they will be forced to Pass. This is acceptable for training purposes.

## Observation Tensor (shape: `[95, 15, 15]`, radius-7 board)

| Planes | Content |
|---|---|
| 0–4 | Player token positions (one plane per player) |
| 5–14 | Meeple colors |
| 15–19 | Post positions |
| 20–24 | Trading center positions |
| 25 | City locations |
| 26 | Current player indicator |
| 27–31 | Common goods totals per player |
| 32–36 | Rare goods totals per player |
| 37–41 | Potential routes per player |
| 42–46 | Active routes per player |
| 47–61 | Individual common goods counts (5 goods × 3 players) |
| 62–76 | Individual rare goods counts (5 goods × 3 players) |
| 77–94 | Per-player, per-region rare good coverage (3 players × 6 regions, binary) |

Planes 77–94 give the NN direct visibility into each player's progress toward the
"rare good from each region" win condition.

## Hyperparameter Decisions and Rationale

### MCTS simulations
Use `--max_simulations 200–400` minimum. At 50 simulations, most of the 100–200+
legal actions get 0–1 visits, producing noisy policy targets.

### skip_timeout_games
Do **not** use `--skip_timeout_games` for MCTS games when win rate is healthy.
The buffer timeout fraction is capped, protecting win signal as a floor.

### Near-win timeout retention
Timeout games where any player has rare goods from 4+ regions, OR a trading center in
Timbuktu AND a desert city (Agadez/Oudane), are retained in the buffer even if
`skip_timeout_games` is active.

### Heuristic guidance
Current plan: hold at `heuristic_guidance_weight = 0.10`. Do **not** decay to zero
until the NN is demonstrably winning without guidance in self-play. Prior runs showed
income farming returns immediately once guidance < 0.05.

### new_rare_region_reward
Currently `0.13` in `mali_ba.ini`. Maximum payoff per player = 5 × 0.13 = 0.65 per game.
This was raised from 0.08 to compete with TakeIncome spam. If income farming persists
despite the no-consecutive-income rule, raise to 0.20–0.25.

### quick_win_threshold
Set to the current median win game length so roughly half of wins earn the bonus.
Check `analyze_log.py` WIN CONDITIONS section before each new run.

### GAMMA
`GAMMA = 0.997`. Long games average 350–450 moves; 0.99 discounts too aggressively.

### Buffer saves
Use `--save_every 30` to reduce blocking pauses when the buffer is written to disk.

### Player balance (not yet implemented)
P0 has a first-mover advantage. Plan: give P1 and P2 a small starting resource handicap
(`starting_resource_handicap` ini flag). Do not implement during an active training run.

## analyze_log.py Usage

```bash
conda activate mali_ba
cd /media/robp/UD/Projects/open_spiel/open_spiel/python/games/mali_ba
python analyze_log.py /media/robp/UD/Projects/open_spiel/train_run07.log
```

The script prompts whether to show the loss chart (matplotlib). Answer `y` or use
`--plot` / `--no-plot` flags.

**Key sections in output:**
- OVERVIEW — games received, throughput, replay buffer breakdown, heuristic guidance (last 10)
- WIN CONDITIONS — win rate, reasons, length percentiles, quick_win_threshold guidance
- WIN-RATE TREND — rolling 15-game window with win type breakdown
- PLAYER WIN BALANCE — per-player win rate (watch for P0 dominance)
- LOSS TREND — per-bucket loss with first→latest comparison
- INTERMEDIATE REWARDS — per-player reward totals and trend
- EARLY TERMINATIONS — value-head-hopeless and near-win-threshold exits
- SURVIVING GAMES — last N games that ran to completion
