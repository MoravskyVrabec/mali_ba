2. The Near-Win Extension — What It Is

Mali-Ba games are long. At max_play_moves (430) the game times out. The extension mechanism lets promising timeout games continue for extra moves so that a win condition that is close to triggering can actually be resolved, producing a richer training signal.

2a. INI Parameters

INI keySectionDefaultCurrentMeaning
max_play_moves[Training]460430Base timeout (play-phase moves only, excluding setup)
near_win_extension_moves[Training]2040Extra moves granted to qualifying games
near_win_extension_value_thresh[MLTraining]0.20.2Leader's value head must exceed this to qualify
clear_winner_thresh[MLTraining]0.350.30Any player's value exceeding this triggers clear-winner exemption

2b. Logic Flow

Python's game loop checks at exactly move_count == base_max_play_moves (i.e., after 430 play moves have been applied, before applying move 431):

  1. Evaluate is_near_win(near_win_rare_regions) and value head.
  2. If (near_win OR clear_winner) AND max_val > 0.20: log extension message, loop continues normally.
  3. Otherwise: early_terminated = True; break — game is discarded (not sent to buffer).

C++ must allow the game to stay non-terminal past move 430 for step 1 to ever run.

3. The Bug — Two-Part Story

3a. Part 1: IsTerminal() used the wrong limit (C++)

The OpenSpiel API method MaxGameLength() in mali_ba_game.h was correctly updated to include the extension:

// mali_ba_game.h — CORRECT
int MaxGameLength() const override {
    return GetMaxPlayMoves() + GetNearWinExtensionMoves() + NumSetupMoves();
    // = 430 + 40 + 10 = 480
}

A quick sanity check confirmed this:

>>> import pyspiel
>>> game = pyspiel.load_game("mali_ba", {"config_file": "...mali_ba.ini"})
>>> print(game.max_game_length())
480

However, the actual terminal check inside IsTerminal() in mali_ba_state_core.cc was never updated and still compared against GetMaxPlayMoves() alone:

// mali_ba_state_core.cc line 1185 — BUG (before fix)
if (PlayMoveCount() >= GetGame()->GetMaxPlayMoves()) {   // 430 — too early!
    is_terminal_ = true;
    game_end_reason_ = "Max game length reached";
    ...
}

A second identical check existed in the win-condition evaluator at line 1402.

Effect: C++ declared the game terminal at 430 play moves (440 total). The Python while loop exited at while not state.is_terminal() before the extension check block was reached. No extension message ever appeared in any log from runs 31 or 32.

Proof from log: Grepping train_run32.log for "Near-win extension" and "base max reached" returned zero matches. All 9 surviving timeout games in run 32 ended at exactly 430 moves.

3b. Part 2: Extension also requires clear_winner (Python)

The original extension check only qualified near_win games. A game exempt due to clear_winner (value > 0.30, e.g. 0.777) was denied extension even though it was clearly heading toward a win — it would be discarded at move 430. This was identified by examining log lines such as:

Actor 100004, Game 25, Move 420: Value check: ['-0.120', '0.777', '0.446'] (thresh=0.10, exempt=clear_winner)

9. Value Head and Win Type Discussion

Is it a fundamental limitation that the value head struggles with two disparate win types? No. The model can represent multi-modal value functions. The structural difference is:

  • Rare goods wins — gradual accumulation; the board state progressively signals value. Value head learns a smooth positive gradient over ~300 moves. This is working.
  • Timbuktu wins — discrete event (trade route completes a coast connection). MCTS finds these via tree search reaching the terminal node in 300–500 simulations. The value head never needed to guide MCTS to find them, so it never learned the pre-win signal. The value head stays negative right up to a Timbuktu win. This is expected behaviour, not a bug — it will self-correct as more Timbuktu win experiences accumulate and the model sees the state-to-win correlation.
